# 结果：同一个 GLM 模型，四个 harness

日期：2026-11-21。模型固定为智谱 `glm-4.7-flash`（免费），设计见 [experiment-design.md](experiment-design.md)。原始数据在 `results/runs.csv` / `runs.json`，每次运行的完整事件流在 `runs/<harness>-<任务>-<次>/`。

样本很小（A 每个 harness 3 次，B 2 次，C 1 次）

## 1. 总表

分数 = 隐藏验收测试通过数。"编译不过" = 结束时 `tsc` 报错（agent 认为做完了，但代码其实是坏的）。

| Harness | A（3 处小改，7 项） | B（跨 4 文件新功能，17 项） | 编译不过 | 编辑失败 / 编辑次数 | 服务端报错 | 自动重试 |
|---|---|---|---|---|---|---|
| Claude Code | 7、7、7 | 14、13 | 0 / 5 | 0 / 29 | 0 | 28 |
| Pi | 7、6、4 | 11、13 | 2 / 5 | 3 / 24 | 23 | 21 |
| OMP | 7、7、2 | 9、8 | 3 / 5 | 20 / 51 | 1 | 0 |
| Pi Durable | 7、4\*、7 | 9、13 | 1 / 5 | 5 / 27 | 4 | 58 |
| Codex† | 4、3、4 | 11、14 | 4 / 5 | 无编辑工具，全用 shell | 0 | （中转层代重试） |

\* durable-A-2 两次都是还没开始就被智谱 529（过载）打断：默认重试 3 次、约 15–25 秒后放弃，一行没改。算作"重试预算不够"，不算"不会写代码"。

† Codex 走本机 LiteLLM 中转，只有 shell 工具，详见第 7 节。

单次耗时（秒）：Claude A 82–130 / B 97–488；Pi A 97–264 / B 449–831；OMP A 130–1200（超时）/ B 170–1154；Durable A 26–77 / B 188–716；Codex A 42–151 / B 124–813。

## 2. 空任务：每个 harness 自带多少上下文

只让它回复"好的"，看第一次请求有多大（`runs/*-P-1`）：

| Harness | 第一次请求的输入 token |
|---|---|
| Claude Code | 约 11,900 |
| OMP | 约 7,200 |
| Pi | 约 1,400 |
| Codex | 约 8,600 |
| Pi Durable（我写的最小指令） | 约 900 |

Claude Code 的系统提示和工具说明是 Pi 的 8 倍多；它在这个弱模型上反而最稳，说明"写得多"不一定是负担。对小模型来说，详细的工具说明和规则可能就是在替它补能力。

## 3. 任务 C：杀进程后恢复

| Harness | 恢复方式 | 杀掉时已改 | 恢复后 | 结果 |
|---|---|---|---|---|
| Claude Code | `--continue` + 一句"继续" | 3 个文件 | 接着改完第 4 个，没有重做 | 13/17，和不打断时一样 |
| Pi | `--continue` + 一句"继续" | 2 个文件 | 4 个文件都改了，但留下未定义的常量 `MAX_ITEM` | 6/9，服务端编译不过 |
| Codex | `codex exec resume --last` + 一句"继续" | 2 个文件（第 23 秒开始改，第 38 秒被杀） | 接着把 4 个文件都改了 | 10/17，服务端编译不过 |
| Pi Durable | `resume()`，**不用再说话** | 3 个文件（第 10 秒开始改，第 25 秒被杀） | 从断点继续，83 秒做完 | 5/9，`save.ts` 逻辑和服务端编译有错 |
| OMP | 原本要用 `--restore` | **两次都没改到文件** | — | 无法测 |

- **Durable 是唯一真正"不用人管"就能接着跑的**：进程被 `SIGKILL` 后重新打开数据库，同一个请求自动从上次停下的地方继续，不需要我再发一句话。另外三个都要靠"把对话历史重新读一遍，再让模型自己猜做到哪了"。
- **OMP 的 `--restore` 只能在交互式终端里用**（命令行模式直接报错 `--restore requires an interactive terminal`），所以无法自动化测试。改用 `--continue` 后，第二次运行又在 20 分钟里一直用 bash 读文件、跑命令（56 次 bash，0 次 edit），没在第一个改动后被杀掉，C 任务对 OMP 实际上没测成。
- 恢复后的质量不比不打断时高，C 主要验证的是"进度丢不丢"，这一点 Claude Code 和 Durable 都没丢。

## 4. 看到的几件事

1. **模型固定时，最大的差别来自"出错之后怎么办"，不是"会不会写"。** 免费 GLM 经常 429/529/网络错误。Claude Code 自动退避重试（C-1 一次就重试了 22 次），从没因此中断；Pi CLI 和 Durable 默认只重试 3 次，Pi 有 23 次请求报错、一次直接 0 改动结束；Durable 有两次还没开始就放弃了。对"便宜但不稳"的模型，重试策略就是可用性。
2. **编辑工具的格式要和模型能力匹配。** OMP 默认用 hashline 编辑（每次编辑要写文件哈希、`PUT N.=M:` 这类头），GLM 经常写错：51 次编辑失败 20 次，报错是 `input must begin with "[PATH#HASH]"`、`payload line has no preceding hunk header`。编辑失败后它会退回去用 bash 改文件，更慢也更容易超时（OMP 有 3 次接近或达到 20 分钟上限）。Claude Code 的"查找-替换"式编辑在 29 次里一次都没失败。
3. **"自己检查一遍再结束"差别很大。** Claude Code 5 次全部能编译；其他三个加起来有 6 次留下了编译错误就宣布完成。
4. **B 任务没有任何一次满分，而且大家错在同一个地方**：服务端那行"居民记得这位玩家以前送来的东西：名字：a、b；名字：c"的格式。这是模型照着中文规格拼字符串的能力问题（也可能是我的规格写得不够显眼），换 harness 没用。说明 harness 能补"流程"，补不了"理解"。
5. **配置不能通用。** OMP 号称兼容 Pi 的配置，但 `apiKey: "$ZHIPU_API_KEY"` 在 Pi 里会展开，在 OMP 里会被当成字面值，返回 401；OMP 要写成不带 `$` 的变量名。
6. **Pi Durable 不是一个 agent，是做 agent 的底座。** 它没有命令行、没有默认系统提示，我写了 100 行运行器才能用。所以它在 A、B 上的分数主要反映我的那几行指令；它真正的优势只在 C 里体现。

## 5. 被重跑的运行

服务器问题导致还没开始就失败的运行，原始记录保存在 `runs/_infra/`：

| 运行 | 原因 | 处理 |
|---|---|---|
| pi-A-1 | 智谱 `Internal Network Failure`，Pi 没恢复，0 改动 | 重跑：7/7 |
| durable-A-2 | 529 过载，重试 3 次后放弃 | 重跑仍是 529，保留为失败 |
| durable-A-3 | 同上 | 重跑：7/7 |
| durable-C-1 | 429，还没改文件就失败，C 测不了 | 重跑：成功恢复，5/9 |
| omp-C-1 | 20 分钟没改文件 + `--restore` 不能无头运行 | 改用 `--continue` 重跑，仍然没在改动后被打断 |

## 6. 局限

- 每格只有 1–3 次，智谱当时的负载对结果影响很大。
- 只测了一个弱模型。换成强模型，编辑格式和重试的差距大概率会缩小。
- Durable 的系统提示是我写的；OMP 的 C 任务没测成。
- Codex 用了中转层和额外的重试，条件和其他四个不完全一样，见第 7 节。

## 7. Codex（0.171）

**接入方式和其他四个不同。** 新版 Codex 只支持 OpenAI 的 Responses 接口（`wire_api = "chat"` 已被删掉，会直接报错），智谱没有这个接口（两个地址都返回 404）。所以中间加了一层本机的 LiteLLM 中转（`config/litellm.yaml`），把请求转到同一个智谱 Anthropic 接口。模型和最终接口一样，但多了一层格式转换。

**数据是等模型空下来后补跑的。** 前三轮（11-21 晚）几乎全部被智谱过载打断：Codex 收到 `Selected model is at capacity` 就整轮结束，最快的一次启动 4 秒就退出了。后来我在中转层加了 3 次重试（和 Pi 默认一样），并写了脚本每 10 分钟测一次模型，等到 11-22 03:36 连续 3 次请求都成功才开跑。所以 Codex 跑的时候，模型比其他四个跑的时候更空闲。三轮失败的记录在 `runs/_infra/codex-*`。

**结果：A 4、3、4（满分 7）；B 11、14（满分 17）；C 10/17。** B 的 14 分和 Claude Code 最好的一次持平，但 A 一次都没做对。

**看到的几件事：**
1. **Codex 是按 OpenAI 自家模型调好的。** 遇到 `glm-4.7-flash` 它提示"找不到模型信息，使用默认配置"，这时只给模型一个 shell 工具，没有它自己的 `apply_patch` 编辑工具（用 `--enable apply_patch_freeform` 也打不开）。于是所有改动都靠 `sed -i` 和 `cat > 文件` 完成。换成第三方模型后，测到的是一个"缩水版"的 Codex。
2. **用 `sed` 改代码，会漏掉 import。** 任务 A 的 3 次全部犯了同一个错误：在 `server/aiProxy.ts` 里把 `3` 换成了 `AVOID_RECENT`，但没加 import，服务端编译不过。它每次都跑了 `tsc --noEmit`，但这条命令只检查前端，看不到服务端的错误，于是它以为做完了。查找-替换式的编辑工具会让模型先读上下文，`sed` 一行命令就不会。
3. **会多改、留垃圾文件。** A-2 改了不该改的 `save.ts`；B-2 留下了 3 个 `.bak` 备份文件，被验收判为越界。
4. **有一次停不下来。** B-2 用了 154 次模型调用、239 次 shell 命令、1100 万缓存 token（其他 B 运行一般 10–60 次调用），反复用 `cat`、`grep` 检查同几个文件。默认配置下没有可用的轮数上限把它拦住。
5. **恢复方式和 Claude Code、Pi 一样**：`codex exec resume --last` 加一句"继续"。被杀时它改了 2 个文件，恢复后 4 个文件都改了，进度没丢，但服务端留下了一个类型错误（`unknown[]` 不能赋给 `string[]`）。
